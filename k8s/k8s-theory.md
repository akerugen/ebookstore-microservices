# Kubernetes
Kubernetes - оркестратор контейнеров. Координирует, где запустить контейнер, когда его перезапустить, как распределить трафик.
Ноды состоят из подов, где node - по сути отдельный компьютер.
У Kubernetes есть Control Plane (Master Node) - как правило, 1 или больше:
* api server (принимает команды)
* scheduler (решает где запустить под)
* controller manager (следит за состоянием)
* etcd (БД со всеми данными)
Kubernetes управляет воркерами (Worker Nodes), их бывает много.
Каждая такая воркер нода состоит из:
* kubelet (агент на ноде)
* container runtime (чаще всего docker)
* pods (приложение1, приложение2 и т.д.)

В проде control plane управляет кластером, а воркеры запускают приложения. 

# Minikube
Minikube - локальная тестовая версия кубов, которая работает на одном ПК.
Minikube нода одновременно состоит из: Control plane + worker:
* api server
* scheduler
* controller manager
* kubelet
* container runtime
* etcd
* pods
Т.е. в minikube есть только один узел (нода), поэтому если его отключить, то весь кластер упадет. Все поды крутятся на одной единственной ноде.
Мощность ограничивается компьютером пользователя.
Все работает в виртуальной машине (Docker Desktop, Hyper-V и т.д.). На винде есть проблемы с одновременным запуском кубов и Docker Desktop.

### Node
Node —  рабочий компьютер (сервер), который входит в состав Kubernetes кластера.
Worker нода состоит из:
* docker/podman: контейнер1, контейнер2, и т.д
* kubelet (агент k8s) - следит за подами, запускает и стопает
* kube-proxy (маршрутизирует трафик между подами)
* cAdvisor (мониторинг)

### Pod
Pod — это самая маленькая единица в кубах, которую можно развернуть.
В поды входят контейнеры. Также сам под входит в сетевой namespace. Все контейнеры одного прода видят друг друга по localhost.
У подов всегда разные id и уникальные ip внутри кластера, соответсвенно внешний мир его не видит. Данные теряются, если не сохранены на диск.
Контейнер в поде задается следующим образом:
```
spec:
  containers:
  - name: auth-service
    image: auth-service:latest
    ports:
    - containerPort: 8082
```

### Deployment
Deployment - инструкция для кубов чтобы запустить несколько копий приложения, а затем управлять ими.
Контроллер реплик задает необходимое ччисло реплик на случай, если какой-то pod упадет. 
При падении одного из подов, ReplicaSet видит это и возобновляет до указанного числа реплик.

Как работает:
1. Отправляется yaml инструкция к deployment:
```
kubectl apply -f 07-auth-service-deployment.yaml

```
2. API сервак получает этот yaml
3. Deployment controller видит это инструкцию
4. Создается ReplicaSet 
5. ReplicaSet создает поды
6. Scheduler распределяет поды
7. Kubelet запускает контейнеры

### Ingress
Ingress — это объект для маршрутизации внешнего трафика на сервисы внутри кластера.
Указывается префикс, и если он совпадает с маршрутом пользователя, то Load Balancer выбирает случайный под.

### HPA
HPA - объект автоматчиеского масштабирования количества подов в зависимости от нагрузки.
В yaml конфиге задается минимальное и максимальное число реплик. Задаются также метрики (например, CPU).
Например, если процент использования выше того процента, что задан в конфиге, то создается еще один pod.
Scale up происходит без задержек, а после scale down есть задержка в ~5 минут.

### Итог
1. Создается yaml конфиг
2. API сервак получает запрос
3. Deployment controller видит новый deployment
4. ReplicaSet controller видит новый ReplicaSet
5. Scheduler распределячет поды по нодам
6. Kubelet на нодах запускает контейнеры
7. Стартует Spring Boot
8. Service обнаруживает поды
9. Ingress маршрутизироует внешний трафик
10. HPA мониторит нагрузку
